Case study · OneAlgo · Algomus (Algo)

From Redshift
to Snowflake.

How I moved OneAlgo's data layer across three platforms, cut downstream reporting time by 30%, and kept the file and EDI integrations around it running.

RoleSenior Software Engineer
CompanyAlgomus (Algo)
Period02/2024 — present
Scope1 TB+ of enterprise data
01

Where it started

OneAlgo's data layer lived on a legacy architecture in AWS Redshift. Algo's management decided to move it to Azure Databricks, with one main goal: bring the running cost down.

02

Redshift to Databricks

I orchestrated the migration of the legacy data architectures to Azure Databricks, moving the notebooks over one by one, with Spark for processing and Delta Lake for storage. Pipelines were built and optimised in Azure Data Factory, alongside SQL and EDI integrations.

While the notebooks were still moving, the cost looked good. A few months after they were live, the picture changed: the bill was almost the same as Redshift, a difference too small to justify the switch.

How it was run
Syntax translation
Redshift and Databricks name and write some functions differently, so each notebook's code was adapted to Databricks syntax, one notebook at a time.
Check per notebook
Every translated notebook was checked on its own before moving on to the next one.
Parallel run
Redshift and Databricks ran side by side on live data, so any difference could be traced back to a specific notebook.
03

Databricks to Snowflake

So the team took one more step, to Snowflake. That move took more than 1 TB of enterprise data out of Azure Databricks. I restructured the data models and optimised query performance, which made downstream reporting 30% faster.

The key change in the pipelines
Before ADF pipeline→Notebook activity→Databricks notebook
After ADF pipeline→Lookup activity→Snowflake notebook

In the Azure Data Factory pipelines, I removed the Databricks notebook activities and added Lookup activities in their place. The Lookups now call the notebooks that run in Snowflake.

Why Snowflake
Modern platform
The latest technology, and the best option the team saw for a modern data platform.
Pay as you go
Compute is billed by usage, so cost follows what actually runs.
Lowest cost
Even after every notebook was migrated, it has been the cheapest of the three so far.
Recoverability
Deleted or removed data can be recovered for up to 90 days.

I used the same method as in the first move: translate the syntax, check each notebook, and run Databricks and Snowflake in parallel on live data. That made it possible to trace exactly which notebook was causing an issue, if any. For this move I also wrote pre- and post-migration scripts, so the data could be verified properly before and after each step.

04

Keeping it running

Around the platform work, I support production-critical file-based and EDI integrations: root-cause analysis across distributed systems, and monitoring of jobs, file flows and system health in ActiveXperts, plus secure AS2 / EDI B2B integrations.
